Datacenter map source, scoring, and experience review — September 7, 2026

The map works as an exploratory state comparison, but its precise rankings imply more certainty than the underlying evidence supports. The largest improvement would be to make the evidence and assumptions inspectable while letting people save and compare scenarios.

Scope: inspected the source and generated page, exercised the page in Chromium at desktop and mobile sizes, compared every electricity price with EIA, checked access to all 47 distinct URLs in the methodology and state citations, and read the principal policy sources. This is not verification of every sentence in all 50 state notes or validation of all 400 judgment ratings. No application code or scores were changed by this review.

**What the current algorithm and controls do**

The weighted arithmetic mean is understandable and worth retaining. Its inputs and interaction semantics need work:

1. A one-level judgment change equals 25 factor points. At the default 25% headroom weight, that moves the composite 6.25 points. Changing only ND headroom from 5 to 4 moves it from #1 (77.69) to #5 (71.44), holding all other states fixed. This is a sensitivity example, not a corrected rating or statistical confidence interval.
2. Setting every slider to zero produces a zero score for every state but assigns ranks 1–50 in dataset order. Alabama appears first. The denominator fallback `||1` hides an undefined scenario. Show “Choose at least one priority” and suppress scores and ranks.
3. Set headroom to 40, choose Physical, then Combined: the value returns to the AI default of 25. Viewing another lens destroys the custom scenario. Store view selection separately from user weights.
4. Seven states with prices from 16.21¢ to 34.13¢ all receive a zero power-cost score because the formula clips at 13¢. That is a substantive preference assumption, not an EIA property. Label the cutoff and let advanced users change economic anchors.
5. The default ND–TN gap is only 1.00 point. Fifteen adjacent pairs in the default ranking display identical rounded scores but different ranks. Use honest ties for exactly equal values and sensitivity information for close values; adding decimal places will not resolve judgment uncertainty.
6. “Strongest/weakest” and detail bars show unweighted factor values. They can highlight a factor assigned zero importance. Add each factor's weighted contribution and show what caused a score or rank to change.
7. Momentum overlaps with ecosystem maturity and can reward the same development pipeline that consumes headroom. Use momentum as context by default, with an explicit optional weight for users who want it.
8. Cheap power can offset an impossible deadline or an applicable permit prohibition in an additive score. Separate known eligibility constraints from preferences. The current data cannot determine actual available MW or connection dates.
9. The color ramp clips below 30 and above 80 despite scores spanning 0–100. Add numeric legend anchors so users can interpret saturation. Keep the same scale across scenarios.
10. The fixed scatter axes do not move with slider changes, although dot colors do. Label the axes as fixed reference scores. Political posture, regulatory predictability, and project momentum are different concepts; a cost-allocation rule need not imply an unfavorable delivery process.

**Recommended scoring design**

Use three separate outputs: requirement status, preference fit, and evidence quality.

Requirement status should be “known conflict,” “no identified conflict,” or “unknown,” evaluated against the project's size, utility territory, timing, and relevant exemptions. Unknown must never silently pass. At state level, many answers will remain unknown; the UI should show a diligence question rather than invent months-to-power from a 1–5 rating. Apply exclusions only where evidence establishes that the selected requirement is not met. Allow users to see excluded candidates and the reason.

For preferences, keep `fit = sum(importance × factor utility) / sum(importance)` when total importance is positive. Explain that fit measures agreement with the selected preferences, not probability of project approval. Keep normalization anchors fixed across filters and comparison sets to avoid ranks changing merely because a state was hidden.

Group the controls into delivery (headroom and permitting), economics (power and incentives), operating conditions (water, cooling, hazards), and connectivity. Let users expand groups into the existing factors. If groups receive weights, normalize the factor weights within each group so a group does not matter more merely because it has more factors. Presets are editorial starting points to test with users; there is no empirically established optimal set here.

Keep reported prices separate from scenario assumptions. An operating-cost scenario could expose load, utilization, PUE, tariff/rider assumptions, taxes, and applicable dates. Show each adjustment separately and avoid charging the same tax again through an opaque policy penalty. Do not simply add current charges to a historic average without checking which components it already includes. Cooling technology should affect modeled water and energy assumptions, with unknown quantities visibly unknown.

For judgments, document what each level means for each factor, its evidence, geography, and date. Offer a transparent “one level better / worse” sensitivity view before introducing simulations. Show rank changes and a shortlist that remains competitive under those specified perturbations. Do not label arbitrary perturbations as probabilities or confidence intervals. Confidence belongs beside the score, not as a multiplier that systematically penalizes sparsely documented states.

Each factor record should retain: reported value and unit, observation period, geographic scope, source IDs, checked date, measured/estimated/judgment type, rationale, and any defensible range. Each policy event additionally needs proposed/enacted/in-force/expired status, effective dates, thresholds, exceptions, and the provisions it supersedes. A source being available does not verify every claim associated with it.

**Recommended user experience**

The primary loop should be: choose a scenario → adjust priorities → see what changed → compare candidates → inspect evidence → save/share.

| User action | Interface response |
|---|---|
| Arrive | Show the map, a compact top-candidate list, an explicit editorial preset, and a short disclosure that most ratings are analyst judgments. Keep the existing fast, self-contained delivery. |
| Adjust a priority | Use relative importance controls with visible effective shares, e.g. “35% of your score.” Keep other raw controls still while shares normalize. Show score contributions and rank movement against a pinned baseline. |
| Explore another lens | Change the view without overwriting the scenario. Returning to Combined restores the user's work. |
| Compare | Pin two to four states with aligned rows for raw facts, weighted contributions, restrictions, unknowns, and sources. Keep the comparison order stable while adjusting weights. |
| Challenge a rating | Put a clearly marked personal override behind “Change this assumption.” Preserve the original value, evidence, and reset action. Separate changing a preference from changing a fact assumption. |
| Inspect evidence | Open a source drawer from the relevant factor, showing what the citation supports, date, geography, and limitations. Missing factor evidence should be visible without hunting through the bibliography. |
| Save or share | Encode scenario, selected states, overrides, data version, and model version in a shareable URL; provide copy-link feedback and reset/undo. Explain a data-version mismatch when loading an older scenario. |
| Use a phone | Keep map/results accessible while opening priorities in a sheet or collapsed panel. Put selected-state details close to the selection. The current page places weights about 855px down and details about 1,747px down at 390px width. |

Preserve keyboard selection of map states. Add actual buttons and `aria-sort` to table headers, keyboard access to scatter points and state rows, and accessible names that include current values. Current table sorting and scatter selection only have click handlers. Keep announcements concise while a slider is being dragged. The desktop map has substantial empty space beneath it while the full slider panel determines the grid height; a compact candidate list or state detail can use that space.

Implement in this order: correct disclosures and source mismatches; fix zero weights and lens persistence; add effective shares, baseline deltas, comparison, and scenario sharing; then add overrides and explicit sensitivity. Rich project constraints and modeled costs should follow the necessary utility, site, tariff, and timing data.
